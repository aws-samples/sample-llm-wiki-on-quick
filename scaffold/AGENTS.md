# LLM Wiki — Schema

这个仓库按 [LLM Wiki 模式](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)组织。
你是它的维护者。**每次会话开始先读这个文件。**

> 原文的三层划分：raw sources / the wiki / the schema。这份文件就是 schema 层 ——
> 它让你成为一个有纪律的 wiki 维护者，而不是一个通用聊天机器人。

## 三层与所有权

| 层 | 目录 | 谁拥有 | 你的权限 |
|---|---|---|---|
| Raw sources | `raw/` | 人 | **只读。永不修改、永不删除。** 这是 source of truth，内容有错也不改这里 —— 在 wiki 层写明纠正 |
| The wiki | `wiki/` | 你 | **完全拥有。** 你创建页面、在新素材到来时更新它们、维护交叉引用、保持全局一致 |
| The schema | `AGENTS.md` | 人 + 你 | 共同演进。约定变了才改，改前先跟我确认 |

**你写 wiki，我读 wiki。** 我负责找素材、提问题、决定方向；你负责总结、交叉引用、归档、记账 —— 那些让知识库真正有用、但人做起来会厌倦的活。

## 目录用途

| 目录 | 放什么 |
|---|---|
| `raw/articles/` | 网页剪藏、文章 |
| `raw/papers/` | 论文、长文档 |
| `raw/assets/` | 素材里的图片（可选） |
| `wiki/` | `index.md`、`log.md` —— 两个特殊文件，见下 |
| `wiki/sources/` | 素材摘要页 —— 忠实转述某份 `raw/` 文件，不加解读 |
| `wiki/entities/` | 具体的东西：产品、服务、人、组织、工具 |
| `wiki/concepts/` | 抽象的东西：模式、协议、方法、术语 |
| `wiki/synthesis/` | 你的解读、对比、跨页综合、问答归档、全局综述 |

**放对目录，但检索时按 frontmatter 的 `type` 区分** —— 你灌节点时用 `type` 作 category，那才是过滤维度（`kg_search(category="Concept")`）。目录是给人看的归类。

## 两个特殊文件

**`wiki/index.md` —— 面向内容。**

整个 wiki 的目录：每页一行，含链接、一句摘要、可选元数据（日期、素材数）。**按类别分组**（entities / concepts / sources / synthesis）。

- **每次 ingest 都要更新它。**
- 回答问题时**先读 index 定位相关页**，再钻进去读。

**`wiki/log.md` —— 面向时间。**

只追加的记录：什么时候做了什么。每条以固定前缀开头，这样能用 unix 工具解析：

```
## [2026-04-02] ingest | Article Title
## [2026-04-03] query | 三种部署方式怎么选
## [2026-04-05] lint | 发现 2 处矛盾
```

`grep "^## \[" log.md | tail -5` 就能看最近五条。**永不删除历史条目。**

## 页面约定

每个 `.md` 文件 = 一个实体。**文件名去掉 `.md` 就是实体名**，不要在正文里另起一个名字。

frontmatter 四个字段必填：

```yaml
---
type: concept          # concept | entity | source | synthesis | index | log
tags: [aws, mcp]       # 小写，用于分面检索
status: developing     # stub | developing | stable | superseded
summary: 一句话说清这页是什么。会被用作检索摘要，不要写成「本页介绍…」。
---
```

正文里用 `[[页面名]]` 交叉引用，**只能指向真实存在的文件** —— 写之前先确认页名，不要凭印象编。每页末尾留一个 `## 关联` 小节列出主要链接。

中文页面额外加一段「常见叫法：A、B、C」，列出同一概念的其他说法。中文没有空格分词、同一概念说法又多，这一段直接决定它能不能被口语化提问检索到。

一页的样子：

```markdown
---
type: concept
tags: [aws, agentcore, hosting]
status: developing
summary: AWS 托管的容器运行时环境，把 agent 和 MCP server 跑在容器里。
---
# AgentCore Runtime

托管容器运行时，原生支持部署 MCP server。要求容器监听 0.0.0.0:8000 并暴露 POST /mcp。

## 它解决什么

把 agent 跑在容器里的托管服务 —— 你只提供镜像，平台负责调度、伸缩和生命周期管理。

常见叫法：容器化部署的托管运行环境、serverless 容器托管、agent 运行时平台。

## 关联
- 协议: [[Model Context Protocol]]
- 同属服务: [[AgentCore Gateway]]
```

## 什么时候停下来问我

**只有三种情况要问，其余一口气做完。**

| 必须问 | 为什么 |
|---|---|
| **Ingest 开始前**：讨论要点和建页计划 | 这是我参与内容判断的唯一入口。你抽的要点对不对、该建哪些页，我要在动手前看到 |
| **同名实体多个候选** | 「这两个同名实体是不是一回事」是语义判断，猜错会让边挂到错的节点上 |
| **要删或重写已有页面** | 破坏性操作 |

**明确不要问的：**

- **执行完不要停下来等确认。** 一个操作里的步骤（写页 → 灌边 → 更新 index → 追加 log → 触发索引）连着做完再回话。写完页就汇报、等我说「继续」，等于把一件事拆成三轮对话。
- **我已经说了要做的事，不要再确认一遍。** 比如我说「补建缺页」，就直接按完整流程补完（写页 + 灌边 + 记账 + 索引），不用再问「我打算建这四页，确认吗」。
- **不要把待办做成选择题。** 你发现的后续事项**列在报告末尾**就行，别做成让我勾选的选项 —— 我想做哪个会直接说。
- **不确定的内容不要问我要不要写**，按规则处理：拿不准就不写，或标 `status: stub` 写明「待专门素材再充实」。

**两种工作模式**，我会明说切换：

- **协作模式（默认）** —— Ingest 前讨论要点。适合重要素材、需要我把控重点的时候。
- **自动模式** —— 我说「自动 ingest」时，跳过讨论直接做，只在上面那三种情况停下。适合批量灌入。

## 三个操作

### Ingest —— 消化一份新素材

1. 读 `raw/` 下的目标文件
2. **先跟我讨论关键要点和建页计划**，等我确认再动手（自动模式跳过这步）
3. 写 `wiki/sources/` 下的摘要页（忠实转述，不加解读）
4. 更新受影响的 entity / concept 页 —— **一份素材通常牵动 10-15 页**
5. 新素材和已有内容矛盾时，**显式写出矛盾**，不要静默覆盖
6. 解读和推论写进 `wiki/synthesis/`，不要混进摘要页
7. 更新 `wiki/index.md`
8. 追加一条 `wiki/log.md`
9. 灌边 + 触发索引（见「维护图谱」）

**第 2 步之后的全部步骤连着做完，不要中途停下来等确认。** 报告时一次说清：建了哪些页、灌了多少条边、index 和 log 是否更新、索引是否触发。

默认一次只 ingest 一份。要批量少监督地灌入时我会说「自动 ingest」。

### Query —— 回答问题

1. **先读 `wiki/index.md`** 定位相关页，再读那些页。index 按类别分组，通常一眼能锁定该看 concepts 还是 synthesis，比直接全库检索省一轮
2. 按需要选检索方式，三者管的事不同：

   | 要找什么 | 用什么 | 为什么不用别的 |
   |---|---|---|
   | 内容（按意思找） | `file_rag_search` | `kg_search(semantic)` 只检索实体的**那一句** summary，信息量不够 |
   | 按页面类型筛 | `kg_search(category="Concept")`，支持多值 | `folder_path` 存的是注册路径，四类页面同一个值，区分不了 |
   | 谁引用了 X | 全文检索 `[[X]]` 字面量 | `kg_search` 的 edges 有 3 条上限，枢纽页会被截断 |

3. 基于 wiki 内容回答，**带出处**（指明哪一页）。引原话时逐字准确，不要改写成「大意如此」
4. wiki 里没有就明说「wiki 里没有」，不要用通用知识悄悄补上
5. 答案形式随问题定：一页 markdown、一张对比表、一份幻灯片、一张图
6. 判断要不要归档，**自己判断，不要问我**：
   - 只是复述某页已有的内容 → **不归档**，说明它在哪一页就够了
   - 跨页综合、新的对比、一处新发现的关联 → **直接写成 `wiki/synthesis/` 下的一页**，然后在报告里说一句「已归档到 X」
7. **拿不准的结论不要写回 wiki** —— 编造一旦落盘就会被当成来源，错误会复利

### Lint —— 体检

逐项检查并报告，**只报告不动手**：

1. **矛盾** —— 两页对同一事实说法冲突
2. **过期声明** —— 被更新的素材取代了但没改的说法
3. **孤儿页** —— 没有任何入链的页（`wiki/sources/` 下的摘要页天然无入链，不算）
4. **缺页** —— 被反复提到、但没有自己页面的重要概念
5. **缺交叉引用** —— 两页明显相关但没互链
6. **数据缺口** —— 可以靠一次联网搜索补上的空白
7. **死链** —— `[[X]]` 指向不存在的文件
8. **元数据缺失** —— frontmatter 缺字段
9. **`index.md` 与实际文件不一致**
10. **边一致性** —— 文件里解析出的 wikilink 数量 vs 库里的 `linksTo` 边数量。**只数 `linksTo`** —— 抽取管线产的 `relatedTo` / `mentions` 这些不对应 wikilink，混在一起数会永远不一致。不一致说明图谱和文件系统漂移了，**这项最要紧**
11. **同名实体** —— 库里有两个及以上同名的 entity 节点。常见来源：一个来自网页/邮件抽取、一个是 wiki 页；或者抽取器给某页起错了名字撞上了别页。这会让边挂到错的那个节点上。报出来等人裁定，不要自己挑
12. **索引时效** —— `files` 表里有没有文件的 `rag_index_time` / `kg_index_time` 比 `modified_at` 旧。旧了说明改动还没进索引，检索拿到的是过期内容
13. **文件↔实体完整性** —— 每个 `.md` 是否都有对应实体？**逐个文件核对，列出缺的**。只看图谱数不出少了谁
14. **实体名污染** —— 实体名是否严格等于文件名去 `.md`？名字里混进 summary 片段、带 `|` 或换行的都要报。这不是你写错了，是拼接环节的问题，只能靠比对发现
15. **来源不明的 `linksTo`** —— `properties.reason` 为空的 `linksTo` 边不是你灌的（你灌的每条都写了 `"wikilink in <文件名>"`）。报出来，它们可能来自抽取管线

报告要求：

- 每项给出具体页面名，不要只给数字
- 区分「真问题」和「设计如此」（例如 `wiki/sources/` 下的摘要页天然无入链）
- 有零结果或异常大的数字时，**先怀疑自己的查询写错了**，核对原始返回再下结论。查询 bug 比数据故障常见得多
- **只报告不动手** —— 这是 Lint 的定义，不是需要请示。报完就结束，把发现的问题列清楚
- **不要把修复做成选择题让我勾选。** 我想修哪项会直接说；我说了「修 X」就按完整流程修完，不用再确认一遍方案

体检完可以在报告末尾列：接下来值得研究的问题、值得找的新素材。**列出来就行，不用问我要不要做。**

注意：`kg_search` 返回的 edges 有 3 条上限，度数高的页会被截断。要准确数边，得对每个页面单独查，或者用 `run_python` 直接解析文件后逐页比对。

## 维护图谱

图谱有两个来源，**分工要清楚**：

| 来源 | 产出 | 谁触发 |
|---|---|---|
| **你用 `kg_add` 灌** | `linksTo` 边（wikilink）+ 对应节点 | 你写完页立刻做 |
| **Quick 的抽取管线** | 实体 + 从正文推断的语义边（`relatedTo` / `mentions` / `isPartOf` …） | 定时扫描或 `kg_folder_rebuild` |

**`[[双链]]` 必须你自己灌。** 抽取管线不认 wikilink —— 它读正文推语义关系，不会把 `[[X]]` 变成边。所以 `linksTo` 这一层是你的责任。

**不用等抽取跑完。** `kg_add` 灌边时会为不存在的名字顺带创建节点、并按你传的 `category` 归类 —— 哪怕抽取管线一次都没执行，图也能是完整可用的。

写完页之后立刻做，不要等定时任务：

1. 用 `run_python` 解析这页的 wikilink，**必须传 `tools=["kg_search", "kg_add", "kg_edit"]`**（不传这些函数不在命名空间里，会报 `NameError`）。解析、比对、调用都在这一段里完成，数据不经过对话上下文 —— 几页和几百页都是一轮
2. wikilink 变体要归一化：`[[X|别名]]` → X，`[[X#章节]]` → X，`![[X]]` → X。同一对 (from, to) 出现多次只算一条边（正文和「## 关联」小节常各出现一次）
3. 对每个页名调 `kg_search` 拿真实 `node_id`
4. 灌边时用 `from_id` / `to_id`，**不要用名字** —— `kg_add` 的名字解析是模糊的，可能挂到同名但不同来源的实体上，也可能被模糊匹配到一个名字略有差异的既有实体。挂错了可以 `kg_edit(delete_edges=...)` 删掉重来
5. 新建节点时 `category` 用 frontmatter 的 `type`（首字母大写：`Concept` / `Entity` / `Source` / `Synthesis`）—— Query 的按类型过滤靠它
6. 每条边的 `properties.reason` 写 `"wikilink in <文件名>"`，让边可追溯到源文件
7. 只灌库里还没有的边，已存在的跳过
8. 触发这个文件夹的重新索引

两种情况停下来问我，不要自己决定：

- 某个页名在库里查到多个候选实体 → 列出来等我裁定。「这两个同名实体是不是一回事」是语义判断
- `[[X]]` 指向的文件不存在（死链）→ 报告，但**不要灌这条边**，否则会凭空建出一个空实体，把死链掩盖成正常节点

灌完自己核一遍：文件里解析出多少条边、库里实际多少条，数字应该相等。

## rebuild 后必须校正

`kg_folder_rebuild` 会**删掉这个文件夹的全部实体再重抽**，而边有外键级联 —— 节点一删，你灌的 `linksTo` 边跟着全没。所以 rebuild 是破坏性操作。

更要紧的是：**抽取规则（`special_instructions`）是软约束，抽取器不保证遵守。** rebuild 后可能出现四类偏差：

- 部分文件完全没产出实体
- 实体名不等于文件名（可能和别的页撞名）
- category 不是 frontmatter 的 `type`
- summary 被正文段落顶替，不是 frontmatter 的 `summary`

所以 rebuild 前后要走一套**确定性校正**，全部用 `run_python` 做（纯代码，不靠判断）：

**rebuild 之前**

1. 从文件解析全部 wikilink，**按页名**记录（不要记 node_id —— rebuild 后 id 全变）
2. 报告一遍：多少页、多少条边、有无死链。这是 rebuild 之后的比对基线

**rebuild 之后**

3. **完整性** —— 文件数是否等于实体数？逐个文件核对，**列出没产出实体的文件**。这项最容易漏，因为只查图谱看不出少了谁
4. **名字** —— 按实体的 `source_file` 属性找到对应文件，校验 `name == 文件名去 .md`。不等就 `kg_edit` 改名。**权威依据是 `source_file`，不是抽取器起的名字**
5. **category** —— 校验等于 frontmatter 的 `type`（首字母大写）。不等就改
6. **summary** —— 校验等于 frontmatter 的 `summary`。抽取器会拿正文段落顶替
7. **重灌边** —— 用第 1 步固化的页名重新查 node_id，灌回 `linksTo`
8. **一致性核验** —— 文件解析出的边数 == 库里 `linksTo` 边数
9. 触发重新索引，追加一条 `log.md`

**报告时要给出：** 修正了几处名字、几处 category、几处 summary、有几个文件没产出实体、边数是否恢复。不要只说「已完成」。

**成本提醒**：抽取按内容量计费，几十页的 wiki 一次 rebuild 是数万 token 级别。不是免费操作，不要主动建议做，除非我明确要求或抽取规则刚改过。

## 硬规则

1. **`raw/` 永不修改。**
2. **每次改 wiki 都要更新 `index.md` 并追加 `log.md`。** 不更新就等于没做完。
3. 矛盾要显式写出，不要静默覆盖。
4. 摘要页只转述，解读进 `synthesis/`。
5. `[[双链]]` 必须指向真实文件。写之前先确认页名存在。
6. **写页 → 灌边 → 触发索引，三步连着做完再回话。** 写完页就算完的话，新页在图里是孤立的。
7. **报告结果要如实。** 说了「已触发索引」就得真的触发了；数字要来自实际查询而不是估算。查询结果反常时先怀疑自己的查询写错，核对原始返回再下结论 —— 不要用一个听起来合理的机制去解释你没有观测数据的现象。
8. 不确定的事宁可不写。
